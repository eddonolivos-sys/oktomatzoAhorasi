1. Tecnologías del stack

Cada tecnología fue elegida por criterios específicos. La siguiente tabla resume la decisión y las alternativas descartadas:

Componente Elección Alternativas descartadas Justificación
Shell (orquestador) Lit + Web Components + Vite React, Svelte, Vue, Vanilla JS Lit compila a Web Components nativos sin runtime. 5 KB contra ~40 KB de React. Cualquier framework puede consumir Web Components. Sin lock-in.
Sub-apps Stack libre (React, Three.js, Vue, vanilla…) — Cada app elige su tecnología. La shell no impone restricciones. El iframe aísla completamente el contexto.
Backend API Go 1.22+ Node.js/Express, Python/FastAPI, Java/Spring, Ruby/Rails Un solo binario estático (~15 MB), sin dependencias de runtime. Rendimiento excelente en VPS de 1 GB RAM. Tipado fuerte, compilación rápida, excelente stdlib. Curva baja para equipos diversos.
Base de datos SQLite PostgreSQL, MySQL, Supabase, PocketBase Cero operación. No requiere servidor, no consume puertos, no hay que configurar replicación. Para <50 usuarios concurrentes rinde perfectamente (~1M requests/día). El backup es copiar un archivo.
Proxy inverso Caddy 2 Nginx, Traefik, HAProxy, Apache HTTPS automático vía Let's Encrypt con cero configuración. Caddyfile legible (no la verbosidad de nginx.conf). Binario estático. Ideal para despliegues pequeños.
Contenedores Docker + Docker Compose Kubernetes, Nomad, serverless Kubernetes es overkill para 2-5 apps y <50 usuarios. Docker Compose es suficiente: define servicios, redes y volúmenes en un archivo YAML.
Comunicación postMessage Shared Worker, BroadcastChannel, estado compartido, eventos del DOM postMessage es el único mecanismo que funciona a través de iframes con aislamiento total. No comparte memoria, no requiere same-origin estricto, es asíncrono y verificable por origen.
Gestor de paquetes pnpm npm, yarn Más rápido que npm, usa hard links para evitar duplicar dependencias en el monorepo. Estrictamente no se usa npm por seguridad (ataques a la cadena de suministro).
Monorepo pnpm workspaces Nx, Turborepo, Lerna pnpm workspaces es nativo, sin dependencia extra. Mismo equipo, <10 apps: un solo repositorio es más simple que múltiples repos con dependencias cruzadas.

¿Por qué iframes y no micro-frontends?

Decisión fundamental de la arquitectura. Los iframes se eligen sobre micro-frontends (single-spa, Module Federation, Web Components) por tres razones:

  1. Aislamiento total — CSS, JS global, variables, y contexto WebGL viven en documentos separados. Una app no puede romper a otra ni por error ni intencionadamente.
  2. Cleanup de GPU — Las apps con Three.js/WebGL son notoriamente propensas a fugas de memoria. Con iframes, al desmontar el elemento, el navegador libera el contexto WebGL automáticamente. En micro-frontends hay que hacerlo manualmente y a menudo falla.
  3. Stack-agnóstico real — Cada app puede usar cualquier tecnología sin coordinación. No comparten runtime, no compilan juntas, no versionan dependencias compartidas.

Trade-off: la UX es menos fluida que una SPA monolítica (sin transiciones animadas entre apps, el iframe es una caja rectangular). Se mitiga con altura dinámica vía postMessage y carga lazy.

2. Arquitectura general

┌──────────────────────────────────────────────────────────────────┐ │ Caddy (Proxy) │ │ :80/:443 → HTTPS + ruteo │ │ hostea la shell en / y redirige /apps/* │ └────┬─────────┬─────────┬──────────┬──────────┬─────────────────────┘ │ │ │ │ │ ▼ ▼ ▼ ▼ ▼ ┌────────┐ ┌────────┐ ┌────────┐ ┌──────────┐ ┌──────────┐ │ Shell │ │ API │ │ App A │ │ App B │ │ Test 1/2 │ │ Lit/WC │ │ Go │ │ React │ │ Three.js │ │ Vanilla │ │ / │ │ /api/* │ │/dashbrd│ │ /viewer3d│ │ /test-* │ └────────┘ └────────┘ └────────┘ └──────────┘ └──────────┘ │ ┌─────────┴──────────┐ │ SQLite │ │ plataforma.db │ └────────────────────┘

Capas de la arquitectura

Capa 1 — Proxy (Caddy)

  • Termina TLS/SSL (auto HTTPS con Let's Encrypt)
  • Rutea por subruta: / → Shell, /apps/* → cada sub-app, /api/* → backend
  • Aplica headers de seguridad (CORS, CSP, X-Frame-Options)

Capa 2 — Shell (Lit/Web Components)

  • Orquestador visual: topbar, sidebar con lanzador de apps, contenedor de iframes
  • Gestiona autenticación (login/register, almacena JWT en sessionStorage)
  • Implementa el protocolo postMessage para comunicarse con sub-apps
  • Carga el catálogo de apps desde la API o desde app-registry.yaml

Capa 3 — Sub-aplicaciones

  • Cada app es un sitio web independiente, servido en su propia ruta (/apps/mi-app/)
  • Se ejecuta dentro de un iframe con atributo sandbox restrictivo
  • Implementa el ShellClient para recibir token y comunicarse con la shell
  • Cada app tiene su propio contenedor Docker y se despliega independientemente

Capa 4 — Backend (Go, arquitectura hexagonal)

  • Dominio — Entidades (User, App) e interfaces de repositorio
  • Servicios — Lógica de negocio: registro, login, CRUD de apps, gestión de usuarios
  • Handlers — Adaptadores HTTP (endpoints REST)
  • Repositorios — Implementación SQLite de las interfaces de dominio

Capa 5 — Persistencia (SQLite)

  • Base de datos embebida, sin servidor. Un solo archivo (plataforma.db)
  • Backup: copiar el archivo. No hay que hacer dump, no hay conexiones que gestionar

3.2 Comunicación shell ↔ sub-app

Toda la comunicación entre la shell y las sub-apps ocurre mediante window.postMessage. No hay estado compartido, variables globales ni almacenamiento común.

Mensajes Shell → App:

TipoPayloadCuándo
auth:token{ token, user }App se carga o usuario inicia sesión
auth:clear—Usuario cierra sesión
theme{ mode }Usuario cambia tema
event:receive{ channel, data }Otra app emitió un evento

Mensajes App → Shell:

TipoPayloadCuándo
app:ready—App terminó de inicializarse
auth:request—App necesita el token actual
navigate{ path }Solicitar navegación a otra app
resize{ height }Reportar altura dinámica del iframe
notify{ type, message }Solicitar notificación en la shell
event:emit{ channel, data }Emitir evento cross-app

3.3 Flujo de datos entre capas

  1. Usuario hace clic en una app del menú lateral
  2. Shell actualiza la URL (pushState) y crea/muestra el iframe apuntando a /apps/mi-app/
  3. Sub-app carga en el iframe, ejecuta su JS, crea un ShellClient
  4. ShellClient envía app:ready a la shell vía postMessage
  5. Shell recibe app:ready y responde con auth:token (token JWT + datos del usuario)
  6. Sub-app recibe el token y lo usa para autenticar sus propias llamadas API
  7. Sub-app reporta periódicamente su altura con resize para que el iframe se ajuste
  8. Cuando el usuario navega a otra app, la shell oculta/elimina el iframe anterior y crea el nuevo

4. Gestión de la plataforma

4.1 Registro de aplicaciones

Las aplicaciones se registran de dos formas:

  • Estática: editando shell/public/app-registry.yaml. La shell lo carga como fallback.
  • Dinámica: mediante la API REST (POST /api/apps, PUT /api/apps/:id, DELETE /api/apps/:id). Las apps se almacenan en SQLite y se sirven desde GET /api/apps.

4.2 Gestión de usuarios

  • Registro e inicio de sesión vía API (/api/auth/register, /api/auth/login)
  • Roles: admin y user
  • Los administradores pueden gestionar usuarios (GET/PUT/DELETE /api/users/:id)
  • Autenticación mediante JWT con expiración (72h por defecto)

5. Primera ejecución

Requisitos

  • Node.js 20+
  • pnpm 9+ (npm install -g pnpm)
  • Go 1.22+
  • Docker + Docker Compose

Pasos

  1. Clonar el repositorio
  2. Instalar dependencias frontend: pnpm install
  3. Generar go.sum del backend: cd backend && go mod tidy && cd ..
  4. Construir frontends: pnpm build
  5. Iniciar servicios: docker compose -f deploy/docker-compose.dev.yml up --build
  6. Abrir http://localhost:8080
  7. Registrar un usuario (nombre, email, contraseña)
  8. Navegar entre las apps del menú lateral
💡 Nota: La primera ejecución construye las imágenes Docker. Las siguientes son instantáneas. Para desarrollo con hot-reload, ejecuta pnpm dev en cada frontend por separado.

6. Protocolo de comunicación shell ↔ apps

El paquete @plataforma/shell-protocol (en packages/shell-protocol/) proporciona dos actores:

ShellOrchestrator (usado por la shell)

import { listen, sendMessage } from '@plataforma/shell-protocol';

const cleanup = listen((event) => {
  if (event.data.type === 'app:ready') {
    sendMessage(event.source, { type: 'auth:token', payload: { token } });
  }
});

ShellClient (usado por las sub-apps)

import { ShellClient } from '@plataforma/shell-protocol';

const client = new ShellClient('mi-app');

client.onToken = (token, user) => {
  // Autenticación lista — configurar API client
};

client.onTheme = (mode) => {
  document.documentElement.setAttribute('data-theme', mode);
};

// Reportar altura
client.reportHeight(document.body.scrollHeight);

// Solicitar navegación a otra app
client.navigate('/otra-app');

// Mostrar notificación
client.notify('success', 'Operación completada');

// Limpiar al desmontar
client.destroy();
⚠️ Importante: Toda sub-app debe implementar ShellClient para recibir el token de autenticación y reportar su altura. Sin esto, el iframe no se ajustará al contenido y la app no podrá autenticarse.

7. Seguridad y aislamiento

Iframes con sandbox

Cada sub-app se carga con el atributo sandbox restrictivo. Valor por defecto:

sandbox="allow-scripts allow-same-origin allow-forms"
  • allow-scripts — necesario para que la app ejecute JS
  • allow-same-origin — permite que la app acceda a cookies y localStorage de su propio origen, y que postMessage funcione
  • allow-forms — permite envío de formularios (solo si la app lo necesita)
  • No se incluye allow-top-navigation — la app no puede navegar la shell
  • No se incluye allow-popups — la app no puede abrir ventanas

Autenticación JWT

  • Token almacenado en sessionStorage (no localStorage — se limpia al cerrar el navegador)
  • Nunca se pasa en la URL del iframe (evita exposición en logs del servidor)
  • Se transmite solo por postMessage, con verificación de origen
  • Contraseñas hasheadas con bcrypt (costo 10)

Aislamiento entre apps

  • CSS: cada app tiene su propio documento, sin colisiones posibles
  • JS global: cada app tiene su propia ventana y contexto de ejecución
  • WebGL/GPU: al desmontar el iframe, el navegador libera contextos WebGL
  • Memoria: si una app fuga memoria, solo afecta su iframe. La shell puede detectar el fallo y recargar solo esa app

9. Solución de problemas

Dockerfile de app falla con "not found" al hacer build desde el directorio de la app

Síntoma: ERROR: failed to solve: "/shell": not found (o similar con packages/, pnpm-lock.yaml) al ejecutar docker build . desde el directorio de una sub-app.

Causa: Este es un monorepo con pnpm workspaces. Los Dockerfiles necesitan tres cosas que viven en la raíz, no en el directorio de la app:

  • pnpm-lock.yaml — lockfile único del monorepo
  • pnpm-workspace.yaml — define qué paquetes son parte del workspace
  • packages/shell-protocol/ — dependencia compartida (workspace:*)

El "build context" de Docker es el directorio que le pasas al comando. Si ese directorio no contiene esos archivos, el COPY falla.

Solución: siempre construir desde la raíz del repositorio

# ✓ CORRECTO — desde la raíz del repo
docker build -f apps/app-b-viewer-3d/Dockerfile -t mi-visualizador .

# ✗ INCORRECTO — desde el directorio de la app
cd apps/app-b-viewer-3d
docker build -t mi-visualizador .   # falla: no encuentra pnpm-lock.yaml

Con docker compose esto ya está configurado: todos los servicios usan context: .. (la raíz) en deploy/docker-compose.dev.yml.

Dockerfile de app copiaba shell/ innecesariamente

Síntoma: Los Dockerfiles de las sub-apps tenían COPY shell/ shell/, lo que significaba que cualquier cambio en el código de la shell invalidaba la caché de build de todas las apps.

Causa: Error de diseño inicial — las sub-apps no dependen de la shell en absoluto. Solo dependen de packages/shell-protocol/.

Solución aplicada: Se eliminó COPY shell/ shell/ de todos los Dockerfiles de las apps. La estructura correcta es:

FROM node:20-alpine AS builder
RUN corepack enable && corepack prepare pnpm@9 --activate
WORKDIR /app

COPY pnpm-lock.yaml pnpm-workspace.yaml package.json tsconfig.base.json ./
COPY apps/ apps/
COPY packages/ packages/
# ← NO hay COPY shell/ shell/ aquí

RUN pnpm install --frozen-lockfile
RUN cd /app/apps/mi-app && node_modules/.bin/tsc -b && node_modules/.bin/vite build

FROM nginx:alpine
COPY --from=builder /app/apps/mi-app/dist /usr/share/nginx/html
COPY --from=builder /app/apps/mi-app/nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80

Base de datos arranca vacía — no aparecen apps en el menú

Síntoma: Al iniciar por primera vez (o tras borrar el volumen backend_data), el menú lateral aparece vacío aunque las apps estén desplegadas.

Causa: La tabla apps de SQLite está vacía. La shell intenta cargar las apps desde GET /api/apps (con token JWT). La API devuelve {"success": true, "data": []} — éxito pero sin datos — y la shell no cae al fallback YAML porque la respuesta fue exitosa.

Solución aplicada: El backend ahora ejecuta un seed automático al iniciar: si la tabla apps está vacía, inserta los 4 proyectos de ejemplo. El seed solo corre una vez (cuando COUNT(*) = 0).

// backend/internal/repository/sqlite.go
func seedApps(db *sql.DB) error {
    var count int
    db.QueryRow(`SELECT COUNT(*) FROM apps`).Scan(&count)
    if count > 0 { return nil }  // ya hay apps, no hacer nada
    // insertar los 4 apps de ejemplo...
}
💡 Nota: Si borras el volumen Docker backend_data, la DB se recrea vacía y el seed vuelve a correr automáticamente.

Error 401 en consola al hacer login por primera vez

Síntoma: POST /api/auth/login 401 (Unauthorized) en la consola del navegador al intentar iniciar sesión.

Causa: El 401 es comportamiento correcto del backend. Ocurre cuando:

  • Se intenta iniciar sesión con un correo que aún no está registrado
  • Se intenta iniciar sesión tras borrar el volumen de datos (la cuenta ya no existe)
  • Se introduce una contraseña incorrecta

Solución aplicada: El frontend ahora muestra un mensaje contextual en español:

  • Login fallido → "Correo o contraseña incorrectos. ¿Primera vez aquí? Usa la pestaña Registrarse."
  • Registro con correo duplicado → "Este correo ya está registrado. Usa la pestaña Iniciar sesión."

Adicionalmente, todos los mensajes de error del backend se tradujeron a español en backend/internal/domain/errors.go.

Decoradores Lit (@state/@property) no disparan re-renders

Síntoma: Hacer click en botones de la UI no hace nada. Asignar this._modo = 'register' no actualiza la pantalla. Los campos del formulario no reaccionan. Todo esto ocurre aunque el código parece correcto.

Causa raíz: TypeScript con target: "ES2022" activa useDefineForClassFields: true por defecto. Esto hace que las declaraciones de campos de clase usen Object.defineProperty, lo que sobreescribe los getters/setters que Lit registra al ejecutar @state() y @property(). El resultado: la reactividad de Lit queda completamente rota silenciosamente.

// tsconfig.json de la shell — configuración correcta
{
  "compilerOptions": {
    "target": "ES2022",
    "experimentalDecorators": true,
    "useDefineForClassFields": false  // ← OBLIGATORIO con Lit + experimentalDecorators
  }
}

Regla: Siempre que uses experimentalDecorators: true con Lit 3.x y TypeScript target ES2015+, añade "useDefineForClassFields": false. Sin este flag, los decoradores se registran pero las propiedades de clase los sobreescriben inmediatamente después.

La sub-app no carga en el iframe

  1. Verifica que la ruta en Caddyfile existe (handle_path /apps/mi-app/*)
  2. Verifica que la app está registrada en app-registry.yaml con la ruta correcta
  3. Verifica que vite.config.ts tiene base configurado (ej: base: '/apps/mi-app/')
  4. Revisa la consola del navegador por errores CORS o de postMessage

El iframe tiene doble scroll

La sub-app debe reportar su altura a la shell mediante client.reportHeight(). Verifica que:

  • El ShellClient se crea correctamente
  • Se llama a reportHeight al cargar y en cada resize
  • Hay un ResizeObserver sobre el document.body
