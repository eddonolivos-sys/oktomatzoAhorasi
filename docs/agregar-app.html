1. Conceptos clave antes de empezar

¿Qué es una sub-app en esta plataforma?

Cada sub-app es un sitio web independiente que se ejecuta dentro de un iframe en la shell. Puede estar construida con cualquier tecnología: React, Vue, Svelte, vanilla JS, Three.js, etc.

La plataforma se encarga de:

  • Autenticar al usuario y pasar el token JWT a tu app vía postMessage
  • Mostrar tu app en la barra lateral y navegar a ella al hacer clic
  • Propagar el tema claro/oscuro a tu app
  • Enrutar el tráfico a tu app a través de Caddy

La estructura del monorepo

Este proyecto usa pnpm workspaces (un monorepo). Todos los archivos de configuración compartidos viven en la raíz:

plataforma/               ← raíz del repo
├── pnpm-lock.yaml        ← lockfile ÚNICO de todo el monorepo
├── pnpm-workspace.yaml   ← define qué carpetas son paquetes
├── tsconfig.base.json    ← TypeScript base compartida
├── packages/
│   └── shell-protocol/   ← paquete compartido (@plataforma/shell-protocol)
├── apps/
│   ├── app-a-dashboard/  ← sub-app React existente
│   ├── app-b-viewer-3d/  ← sub-app Three.js existente
│   └── mi-nueva-app/     ← ← ← aquí va tu app
├── shell/                ← interfaz orquestadora (Lit)
├── backend/              ← API Go
└── deploy/               ← docker-compose.dev.yml, docker-compose.yml
⚠️ Consecuencia para Docker: Cuando construyes una imagen Docker de cualquier app, el build context debe ser la raíz del repo (no el directorio de la app). Más detalles en la sección 4.

3. Integrar el protocolo de comunicación

El paquete @plataforma/shell-protocol ya está en el repo. Lo usas para comunicarte con la shell. Crea apps/mi-app/src/main.ts:

import { ShellClient } from '@plataforma/shell-protocol';

// 1. Crear el cliente con un ID único para tu app
const client = new ShellClient('mi-app');

// 2. Recibir el token JWT cuando el usuario está autenticado
client.onToken = (token, user) => {
  console.log('Autenticado como', user.name, '— rol:', user.role);
  // Guarda el token para usarlo en tus llamadas a la API:
  // fetch('/api/mis-datos', { headers: { Authorization: `Bearer ${token}` } })
};

// 3. Reaccionar al cambio de tema (claro / oscuro)
client.onTheme = (mode) => {
  document.documentElement.setAttribute('data-theme', mode);
};

// 4. Reportar altura dinámica para que el iframe se ajuste sin scroll doble
function reportHeight() {
  client.reportHeight(document.documentElement.scrollHeight);
}
window.addEventListener('resize', reportHeight);
new ResizeObserver(reportHeight).observe(document.body);
reportHeight();

// 5. Opcional — navegar a otra app
// client.navigate('/dashboard');

// 6. Opcional — mostrar notificación en la shell
// client.notify('success', '¡Datos guardados!');

// 7. Limpiar al cerrar
window.addEventListener('unload', () => client.destroy());
💡 ¿Cuándo llega el token? La shell envía auth:token automáticamente cuando el iframe carga (app:ready) y cuando el usuario inicia sesión. Si el usuario no está autenticado, onToken no se llama — el iframe sigue mostrándose pero sin acceso a rutas protegidas.

4. Desplegar con Docker Docker

⚠️ Regla del monorepo: El build context de Docker siempre es la raíz del repo. Los Dockerfiles copian pnpm-lock.yaml y packages/ desde ahí. Si ejecutas docker build . desde el directorio de la app, fallará con "not found".

Paso 1 — Crear el Dockerfile en tu app

# apps/mi-app/Dockerfile
FROM node:20-alpine AS builder

RUN corepack enable && corepack prepare pnpm@9 --activate

WORKDIR /app

# Archivos raíz del monorepo (imprescindibles)
COPY pnpm-lock.yaml pnpm-workspace.yaml package.json tsconfig.base.json ./

# Todas las apps y el paquete compartido
# (COPY apps/ completo: pnpm necesita ver todos los paquetes del workspace)
COPY apps/ apps/
COPY packages/ packages/
# NO incluir COPY shell/ shell/ — las apps no dependen de la shell

RUN pnpm install --frozen-lockfile

RUN cd /app/apps/mi-app && node_modules/.bin/tsc -b && node_modules/.bin/vite build

# Imagen final: nginx sirviendo los estáticos
FROM nginx:alpine

COPY --from=builder /app/apps/mi-app/dist /usr/share/nginx/html
COPY --from=builder /app/apps/mi-app/nginx.conf /etc/nginx/conf.d/default.conf

EXPOSE 80

Paso 2 — Añadir el servicio a docker-compose.dev.yml

Edita deploy/docker-compose.dev.yml:

  mi-app:
    build:
      context: ..                          # ← raíz del repo, no el dir de la app
      dockerfile: apps/mi-app/Dockerfile
    ports:
      - "8087:80"                          # elige un puerto libre en tu máquina

Paso 3 — Añadir la ruta en Caddy

Edita proxy/Caddyfile.dev:

handle_path /apps/mi-app/* {
    reverse_proxy mi-app:80
}

Paso 4 — Construir y levantar

# Desde la RAÍZ del repo
docker compose -f deploy/docker-compose.dev.yml up --build

Construir solo tu app (imagen individual)

# Desde la RAÍZ del repo
docker build -f apps/mi-app/Dockerfile -t mi-app .

# Ejecutar individualmente para probar
docker run -p 8087:80 mi-app
✓ ¿Por qué desde la raíz? El . al final le dice a Docker qué directorio enviar como "build context". El Dockerfile hace COPY pnpm-lock.yaml — ese archivo solo existe en la raíz, no en el directorio de la app. Con -f especificas dónde está el Dockerfile; con . especificas desde dónde copiar.

5. Desarrollo sin Docker Sin Docker

No necesitas Docker para desarrollar tu app. Puedes correr el servidor de desarrollo de Vite directamente:

Instala dependencias desde la raíz (solo la primera vez — enlaza los paquetes del workspace):

# Desde la raíz del repo
pnpm install

Luego corre tu app:

pnpm --filter @plataforma/mi-app dev

O desde el directorio de la app (después del pnpm install raíz):

cd apps/mi-app
pnpm dev
# Desde la raíz
pnpm --filter @plataforma/mi-app dev

# O desde el directorio de la app
cd apps/mi-app && pnpm dev

Tu app estará disponible en http://localhost:5173 (o el siguiente puerto libre).

Para correr todo el stack sin Docker, abre terminales separadas:

# Terminal 1 — Backend Go
cd backend && go run ./cmd/api
# → http://localhost:8080/api

# Terminal 2 — Shell (interfaz principal)
pnpm --filter @plataforma/shell dev
# → http://localhost:5173

# Terminal 3 — Tu nueva app
pnpm --filter @plataforma/mi-app dev
# → http://localhost:5174 (o siguiente puerto libre)
💡 Sin Caddy en modo local: Cada app corre en su propio puerto. La shell no enrutará tu app automáticamente. Para probar la integración completa (shell + routing + postMessage), usa Docker Compose.

6. Registrar la app en la plataforma

Para que la app aparezca en el menú lateral de la shell, debes registrarla. Tienes dos opciones:

Necesitas un token de usuario. Obtenlo iniciando sesión:

# 1. Obtener token
curl -s -X POST http://localhost:8081/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"tu@email.com","password":"tu-contraseña"}' \
  | grep -o '"token":"[^"]*"'
# 2. Registrar la app (reemplaza TOKEN con el token obtenido)
curl -X POST http://localhost:8081/api/apps \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer TOKEN" \
  -d '{
    "id": "mi-app",
    "name": "Mi App",
    "description": "Descripción de lo que hace mi app",
    "icon": "home",
    "route": "/mi-app",
    "src": "/apps/mi-app/",
    "version": "1.0.0",
    "sandbox": "allow-scripts allow-same-origin allow-forms",
    "category": "General",
    "tags": ["mi-tecnologia"]
  }'

Valores del campo icon

Actualmente se usan nombres de iconos como cadena de texto (home, bar-chart, cube). La shell los interpreta para mostrar el icono correspondiente en el menú.

Valores del campo sandbox

ValorCuándo usarlo
allow-scripts allow-same-originApps que solo necesitan ejecutar JS
allow-scripts allow-same-origin allow-formsApps con formularios
allow-scripts allow-same-origin allow-popupsApps que abren ventanas/modales del navegador

Edita shell/public/app-registry.yaml y añade tu app. La shell lo usa como fallback cuando la API no está disponible:

apps:
  # ... apps existentes ...

  - id: mi-app
    name: Mi App
    description: Descripción de lo que hace mi app
    icon: home
    route: /mi-app
    src: /apps/mi-app/
    version: 1.0.0
    sandbox: "allow-scripts allow-same-origin allow-forms"
    category: General
    tags:
      - mi-tecnologia
💡 Cuándo usar el YAML: El YAML es útil durante desarrollo para no tener que hacer login y registrar por API. En producción, la API es la fuente de verdad — el YAML solo sirve cuando la API no responde.

7. Checklist de integración

  • package.json con nombre @plataforma/mi-app y dependencia @plataforma/shell-protocol: workspace:*
  • vite.config.ts con base: '/apps/mi-app/' (barra al final)
  • ShellClient creado con ID único en el código de la app
  • client.onToken implementado para recibir autenticación
  • client.reportHeight() llamado al cargar y en cada resize
  • Tema oscuro/claro soportado via client.onTheme
  • client.destroy() llamado al cerrar/desmontar
  • (Docker) Dockerfile creado sin COPY shell/ shell/
  • (Docker) Servicio añadido a deploy/docker-compose.dev.yml con context: ..
  • (Docker) Ruta añadida en proxy/Caddyfile.dev con handle_path /apps/mi-app/*
  • App registrada vía API o en shell/public/app-registry.yaml
  • Probado: la app aparece en el menú lateral y carga correctamente
  • Probado: client.onToken se dispara después de iniciar sesión

8. Preguntas frecuentes

¿Puedo usar React / Vue / Svelte / vanilla JS?

Sí. La plataforma no impone ninguna tecnología. Tu app puede usar cualquier framework. Solo necesita implementar ShellClient del paquete @plataforma/shell-protocol.

¿Puedo construir la imagen Docker desde el directorio de mi app?

No directamente. El Dockerfile copia pnpm-lock.yaml y packages/ que están en la raíz. El comando correcto es siempre desde la raíz:

docker build -f apps/mi-app/Dockerfile -t mi-app .

Esto es por diseño del monorepo — no es una limitación de Docker sino de cómo pnpm workspaces gestiona dependencias compartidas.

¿Mi app puede llamar a la API del backend?

Sí. Recibe el token JWT a través de client.onToken y úsalo en tus requests:

client.onToken = (token) => {
  fetch('/api/mis-datos', {
    headers: { Authorization: `Bearer ${token}` }
  }).then(r => r.json()).then(console.log);
};

Las rutas de la API disponibles están en backend/cmd/api/main.go. Para rutas nuevas, añádelas al backend Go.

¿Qué pasa si no implemento reportHeight?

El iframe tendrá una altura fija (o la mínima del contenedor), lo que puede causar doble scroll: uno en la shell y otro dentro del iframe. Siempre implementa reportHeight con un ResizeObserver.

¿Puedo tener apps externas al repositorio?

Sí. Una app no tiene que estar en el monorepo para aparecer en la plataforma. Solo necesitas que:

  1. Esté accesible desde una URL (su propio servidor, Netlify, Vercel, etc.)
  2. Implemente el ShellClient del protocolo postMessage
  3. Esté registrada en la API o el YAML apuntando a esa URL en el campo src
  4. La ruta en Caddy apunte a esa URL externa

En ese caso, no necesita Dockerfile ni estar en el monorepo.
